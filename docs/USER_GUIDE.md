# Руководство пользователя: Superlog-lite

Мониторинг вашего локального LLM (ik_llama на порту 8083). Узнавайте о проблемах раньше и настраивайте авто-перезапуск.

---

## Что это?

**superlog-lite** — это лёгкая утилита, которая проверяет ваш локальный LLM-сервер:

1. **Проверяет доступность** — есть ли сервер на `http://localhost:8083/v1`
2. **Проверяет слот генерации** (`/health`) — если занят другим клиентом, проба пропускается → `server_busy`
3. **Тестирует генерацию** — просит у модели сгенерировать 100 токенов и считает, насколько быстро это происходит (токенов/секунду)
4. **Анализирует результат:**
   - ✅ Сервер живой и генерирует быстро → всё ок
   - ⚠️ Медленно (< 10 токенов/сек) → `low_throughput`
   - ⚠️ Долго генерирует (> 30 секунд) → `high_latency`
   - 🛑 Сервер упал → `generation_error` или `server_unreachable`
5. **Запоминает проблемку** в базе SQLite (`incidents.db`) — если она повторится, вы увидите сколько раз уже была
6. **Автоматически перезапускает** сервер при критических ошибках (опция `--no-auto-fix` отключает)

> Паттерн: **След отпечатка (Fingerprint) → Память → Работа агента**. Каждая проблемка имеет свой "отпечаток" — если вы увидите его снова, система подскажет: "эта проблема уже была 3 раза".

## Как установить

```bat
cd F:\superlog-lite
pip install -r requirements.txt
```

> Требуется Python 3.11+. Зависимости: только `Pillow` для иконки (для мониторинга использует стандартная библиотека).

## Как запустить мониторинг

### Разовая проверка (рекомендуется сначала так)

```bat
python monitor.py
```

Пример вывода:

### Без авто-перезапуска (только мониторинг)

```bat
python monitor.py --no-auto-fix
```

### Через лаунчер (удобно в Windows)

```bat
monitor_8083.bat
```

Можно добавить в планировщик Windows или вызывать из `cron`/`supervisor`:

```bat
python monitor.py --no-auto-fix
```

> Запуск каждые 5–10 минут достаточно.

## Как понимать результат

| Что видно | Что значит | Что делать |
|-----------|------------|------------|
| `NO INCIDENTS — server healthy` | Всё работает | ✅ ничего |
| `low_throughput` ⚠️ | Модель отвечает медленно (< 10 токенов/сек) | Проверьте VRAM, нагрузку на GPU, перегрев |
| `high_latency` ⚠️ | Долго включается/отвечает (> 30 сек) | Проверьте загрузку CPU, температуру, swap |
| `server_busy` ⚠️ | Слот генерации занят другим клиентом — проба пропущена | Подождите или найдите клиента, монополизировавшего сервер; рестарт НЕ выполняется |
| `generation_error` 🛑 | Модель падает при генерации | Сервер сломан — `auto_fix` попытается перезапустить |
| `server_unreachable` 🛑 | Сервер не отвечает вообще | Проверьте процесс, порт 8083 |

## Где смотреть историю

Вся история сохраняется в **`incidents.db`** (SQLite). Откройте её любой SQLite-просмотрщик:

- **Таблица `incidents`** — все уникальные проблемки с количеством повторений (`run_count`)
- **Таблица `agent_runs`** — каждая проверка мониторинга (время, статус, что проверялось)

Пример запроса:
```sql
SELECT fingerprint, error_type, run_count, first_seen, last_seen FROM incidents ORDER BY last_seen DESC;
```

## Как настроить пороги

По умолчанию:
- `tok/s < 10` → `low_throughput`
- `latency > 30` сек → `high_latency`
- таймаут пробы генерации: 120 сек
- Авто-перезапуск: каждые 600 секунд (10 минут) между рестартами одной и той же проблемы

Можно переопределить через **флаги**:

```bat
python monitor.py --threshold-tok 20 --threshold-latency 40 --gen-timeout 60
```

Или через **переменные окружения**:

```bat
set SUPERLOG_TOK_S_THRESHOLD=20
set SUPERLOG_LATENCY_THRESHOLD=40
set SUPERLOG_RESTART_COOLDOWN=900
set SUPERLOG_BASE=http://localhost:8083/v1
set SUPERLOG_RESTART_BAT=F:\barozp-opus-8083\run_barozp_8083_mtp.bat
python monitor.py
```

## Частые вопросы (FAQ)

**Q: Авто-перезапуск не работает.**  
A: Проверьте `SUPERLOG_RESTART_BAT` — путь к `.bat` файлу запуска сервера. По умолчанию он ищет `F:\barozp-opus-8083\run_barozp_8083_mtp.bat`.

**Q: Вижу `generation_error: timed out`.**  
A: Сервер завис или слишком медленно генерирует (120 сек). `auto_fix` попытается перезапустить. Если не помогает — проверьте GPU.

**Q: `low_throughput` появляется при каждом запуске с разным `fingerprint`.**  
A: Это была старая бага (C-02) — исправлена. Теперь `tok_s=8.2` и `tok_s=8.3` дают один `fingerprint`.

**Q: Где журналы?**  
A: Выводятся в консоль. База — `incidents.db`. Бэкап старой БД: `incidents.db.pre_fix_bak`.
